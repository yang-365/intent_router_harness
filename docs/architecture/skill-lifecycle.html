Skill 加载与卸载生命周期

Intent Router Harness — SkillLifecycleMiddleware + SkillFileMiddleware + SkillRegistry 协作流程

1. Skill 目录结构与数据模型

1.1 Skill 目录结构

skills/ ├── transfer-routing/ # 转账意图 skill │ ├── SKILL.md # frontmatter(name, description, intent_codes, required_slots, references) + body(意图边界逻辑) │ └── references/ │ ├── slot_filling.md # 提槽规则：必填槽位、提取原则、多轮补槽逻辑 │ └── workflow_request.md # API 调用方式：workflow_api_call 参数组装 └── bill-payment-routing/ # 缴费意图 skill └── SKILL.md # frontmatter + body（无 references 目录）

1.2 SKILL.md Frontmatter 字段

字段类型说明示例
name str 唯一技能名称，用于 Registry 索引 transfer-routing
description str 技能描述，注入 metadata 摘要供 LLM 识别意图 掌银转账意图识别技能
intent_codes list[str] 意图码列表（每个 skill 只允许 1 个） ["AG_TRANS"]
required_slots list[str] 必填槽位列表 ["payee_name", "amount"]
references list[dict] reference 文件清单：id / path / purpose [{"id":"slot_filling","path":"references/slot_filling.md","purpose":"转账提槽规则"}]

1.3 Registry 数据模型（内存中）

类存储内容何时创建
SkillMeta name, description, skill_dir, intent_codes, required_slots, references(SkillReferenceMeta[]) 启动时扫描 SKILL.md frontmatter
SkillReferenceMeta id, relative_path, purpose 启动时从 frontmatter.references 解析
SkillRegistry._skills dict[name → SkillMeta] 启动时构建
SkillRegistry._intent_index dict[intent_code → skill_name] 启动时构建

2. 启动阶段：Registry 初始化

SkillRegistry.from_roots(skill_roots)
TOML spec 中 skill_roots = ["../skills"] 指定扫描目录。 遍历每个 root 下的子目录，找到包含 SKILL.md 的目录。
HarnessConfig.load("spec.toml") → skill_roots = ["../skills"] → SkillRegistry.from_roots(resolved_paths)
解析 Frontmatter（仅元数据，不读 body）
对每个 SKILL.md 调用 _parse_skill_metadata()：
• 用 --- 分割 frontmatter 和 body
• 解析 YAML frontmatter → SkillMeta
• 解析 references 字段 → SkillReferenceMeta[]
• 不读取 body 内容和 reference 文件内容 — 按需加载
_parse_skill_metadata("/skills/transfer-routing/SKILL.md") → SkillMeta(name="transfer-routing", intent_codes=("AG_TRANS",), required_slots=("payee_name","amount"), references=(SkillReferenceMeta(id="slot_filling",...), ...))
校验 + 构建意图索引
• _validate_skill_meta()：每个 skill 只允许 1 个 intent_code
• 检查 intent_code 冲突（同一个 intent_code 不能被两个 skill 声明）
• 写入 _intent_index: {"AG_TRANS" → "transfer-routing", "AG_PAY_BILL" → "bill-payment-routing"}
registry_ready: count=2, skills=[bill-payment-routing, transfer-routing]
关键设计：启动时只解析元数据（frontmatter），不读取 SKILL.md body 和 reference 文件内容。 Body 和 reference 在运行时按需加载，减少初始内存占用，支持大量 skill 注册。

Phase 1 — 元数据注入（意图识别前）

触发条件

_prepare_skill_context() 判断：
target_skill == None 且 self._loaded_skill == None
→ 尚未检测到任何意图，也没有已加载的 skill
_detect_target_skill(messages) → None
扫描所有历史消息（从最新到最旧），两级检测：
• Level 1: JSON intent_code 字段（structured output）
• Level 2: 文本扫描已注册的 intent_code（如 "AG_TRANS" 出现在文本中）
首次用户输入（如"给张三转账500元"）还没有 agent 回复，所以检测结果为 None。
_inject_metadata_summary(request)
调用 SkillRegistry.all_metadata_summary() 生成轻量摘要，注入到 system prompt。
摘要内容：每个 skill 的 name + description + intent_codes + required_slots。
不包含 SKILL.md body，不包含 reference 文件内容。
skill_metadata_injected: 注入 2 个技能摘要用于意图识别
注入 Skill Loading Protocol 指令
在 metadata 摘要后追加指令，引导 LLM 执行正确顺序：
"识别到用户意图后，必须先通过 read_file 读取对应技能的 reference 文件， 了解提槽规则和 API 调用方式，然后再调用 workflow_api_call。 不要编造 workflow URL，必须使用 reference 文件中的完整地址。"
System Prompt（Phase 1 注入后）
## Task Execution Constraints - 任务必须串行执行：一次只推进一个 current_task - 当前任务缺少必填参数时，必须向用户追问... - workflow_api_call 完成后，将状态设为 waiting_assistant_completion... ## Available Skills (Intent Recognition) - **transfer-routing**: 掌银转账意图识别技能 intent_codes: ["AG_TRANS"] required_slots: ["payee_name", "amount"] - **bill-payment-routing**: 识别并处理水电费、话费等缴费意图... intent_codes: ["AG_PAY_BILL"] required_slots: ["payment_item", "amount"] ## Skill Loading Protocol 识别到用户意图后，必须先通过 read_file 读取对应技能的 reference 文件...
Phase 1 目的：LLM 只看到技能名称和描述，可以做意图识别，但不知道提槽细节和 API 地址。 保持上下文精简，避免在意图识别阶段注入不相关 skill 的完整内容。

Phase 2 — 全量加载（意图识别后）

触发条件

_prepare_skill_context() 判断：
target_skill != None 且 target_skill != self._loaded_skill
→ 检测到意图（如 AG_TRANS → transfer-routing），且该 skill 尚未加载
_detect_target_skill(messages) → "transfer-routing"
LLM 在 Phase 1 的 model call 中输出了 AG_TRANS（JSON 或文本中出现）。
第二次 model call 开始前，_detect_target_skill 扫描到该意图码。
• Level 1: 尝试解析 JSON → payload["frames"][0]["intent_code"] == "AG_TRANS"
• Level 2: 文本搜索 → "AG_TRANS" in content
通过 _intent_index["AG_TRANS"] 查找到 skill name = "transfer-routing"
self._loaded_skill = "transfer-routing"
更新内部状态，记录当前已加载的 skill。
_inject_skill_with_references(request, "transfer-routing")
核心加载步骤，调用 _build_skill_block()：
SkillRegistry.load_skill_body("transfer-routing")
从文件系统读取 SKILL.md 的 body 部分（去掉 frontmatter）。
包含：意图边界判定逻辑（Step1~Step4）、示例、路由约束。
skill_loaded: 加载技能: transfer-routing
遍历 meta.references → 逐个加载 reference body
对 frontmatter 中声明的每个 reference：
• slot_filling → 读取 references/slot_filling.md body（提槽规则）
• workflow_request → 读取 references/workflow_request.md body（API 调用方式 + 完整 URL）
每个 reference body 格式化为 ### Reference: {id} — {purpose}\n\n{body}
skill_reference_loaded: 加载 2 个参考文件: slot_filling(转账提槽规则), workflow_request(转账子工作流接口)
组装并替换 system prompt 中的 skill block
• 如果 system prompt 中已有 ## Loaded Skill: 块 → 先截断移除
• 追加新的 skill block：## Loaded Skill: transfer-routing + body + references
• 调用 request.override(system_message=...) 替换 system prompt
System Prompt（Phase 2 注入后 — 新增部分）
## Loaded Skill: transfer-routing # 掌银转账意图识别 用于判断用户是否表达掌银转账意图... ## 第一阶段：转账意图与支持范围判定 ...（意图边界逻辑 Step1~Step4） ### Reference: slot_filling — 转账提槽规则 # 转账提槽规则 - payee_name：收款人姓名 - amount：转账金额... （提取原则、多轮补槽规则） ### Reference: workflow_request — 转账子工作流接口与参数组装说明 # 转账子工作流请求组装 workflow_api_call(method="POST", url="http://127.0.0.1:9877/agent-api/workflow-agent-1-1b14f16b/chatabc/use_as_tool", body={...}) （完整 URL、请求体结构、约束）
Phase 2 目的：LLM 现在拥有完整的业务上下文：
• 意图边界判定规则（SKILL.md body）
• 提槽规则和必填槽位（slot_filling.md）
• 工作流 API 的完整 URL 和参数格式（workflow_request.md）
LLM 可以按照 reference 规则进行提槽，并使用正确的 URL 调用 workflow_api_call。

Phase 3 — 持续注入（同一 skill 的后续 model call）

触发条件

_prepare_skill_context() 判断：
self._loaded_skill != None（已有加载的 skill）
且 target_skill 要么等于 _loaded_skill 要么为 None
→ 同一个 skill 上下文中的后续 model call（多轮提槽、workflow 调用等）
每次 model call 前重新注入 skill block
因为 deepagent 每次 model call 都可能重组 system prompt，
middleware 在每次 wrap_model_call 中调用 _inject_skill_with_references()，
确保 skill body + references 始终在 system prompt 中。
注意：这会导致 skill_loaded 和 skill_reference_loaded trace 重复出现。
skill_loaded: 加载技能: transfer-routing (重复)
skill_reference_loaded: 加载 2 个参考文件... (重复)
Phase 3 目的：保证多轮对话中 LLM 始终能看到 skill 上下文（提槽规则、API 地址）。 即使 deepagent 在中间步骤修改了 system prompt，skill block 也会被重新注入。

4. Skill 卸载与切换

触发条件

_prepare_skill_context() 判断：
target_skill != None 且 target_skill != self._loaded_skill 且 self._loaded_skill != None
→ 检测到新意图（如 AG_PAY_BILL），且当前已加载另一个 skill（如 transfer-routing）
检测到新意图：AG_PAY_BILL → bill-payment-routing
用户输入"帮我缴电费200元"，LLM 输出包含 AG_PAY_BILL。
_detect_target_skill() 返回 "bill-payment-routing"，与当前 _loaded_skill="transfer-routing" 不同。
卸载旧 skill：emit trace + 日志
记录卸载事件。卸载的实际操作是：在下一步构建新的 system prompt 时，
_inject_skill_with_references() 会检测到已有 ## Loaded Skill: 块，
截断该块之后的所有内容，然后追加新 skill 的内容。
没有独立的"清除内存"步骤 — 卸载 = 替换 system prompt 中的 skill block。
skill_unloaded: 卸载技能: transfer-routing

内部状态指向新 skill。
加载新 skill：_inject_skill_with_references("bill-payment-routing")

• load_skill_body("bill-payment-routing") → 读取 SKILL.md body
• 遍历 meta.references → 加载 reference bodies（如果有）
• 截断旧 skill block，追加新 skill block
skill_loaded: 加载技能: bill-payment-routing
System Prompt（卸载 transfer-routing，加载 bill-payment-routing 后）
## Task Execution Constraints ... ## Available Skills (Intent Recognition) ... ## Skill Loading Protocol ... ## Loaded Skill: bill-payment-routing ← 替换了之前的 transfer-routing # 缴费意图路由规则 本 skill 仅用于缴费业务意图 AG_PAY_BILL... （意图边界、标准槽位、补槽规则、任务规划） （注：bill-payment-routing 没有 references 目录，所以没有 Reference 块）

5. SkillFileMiddleware — 虚拟文件读取

作用：拦截 LLM 发出的 read_file tool call，当路径以 /skills/ 开头时， 从 SkillRegistry 加载内容而非访问真实文件系统。让 skill 文件作为虚拟覆盖层存在。
LLM 发出 read_file("/skills/transfer-routing/references/workflow_request.md")
LLM 根据 Skill Loading Protocol 指令，主动调用 read_file 读取 reference 文件。
SkillFileMiddleware.wrap_tool_call() 拦截
• 检查 tool_name == "read_file" ？是
• 提取 file_path 参数
• 标准化路径 → "/skills/transfer-routing/references/workflow_request.md"
• 路径以 /skills/ 开头？ 是 → 进入虚拟解析
_resolve_virtual_path() → 从 Registry 加载
• 解析路径：["skills", "transfer-routing", "references", "workflow_request.md"]
• skill_dir_name = "transfer-routing" → 匹配 meta.skill_dir.name
• file_part = "references/workflow_request.md" → 匹配 ref.relative_path
• 调用 SkillRegistry.load_reference("transfer-routing", "workflow_request")
• 返回 reference body 作为 ToolMessage content
skill_file_read: 读取: /skills/transfer-routing/references/workflow_request.md
路径不存在？返回可用文件列表
如果 LLM 请求的路径在 /skills/ 下但不匹配任何已注册的文件：
• 调用 virtual_file_listing() 获取所有已注册 skill 的虚拟路径
• 返回 "File not found" + 可用文件列表，帮助 LLM 自我纠正

9. 设计约束与边界

约束说明
一个 skill 一个 intent_code _validate_skill_meta() 强制：len(intent_codes) <= 1
intent_code 全局唯一 同一个 intent_code 不能被两个 skill 声明，否则启动时抛 ValueError
业务逻辑在 skills/，不在框架 middleware 不包含任何 intent code、slot name、API URL。全部来自 skill 文件
卸载 = system prompt 替换 没有独立的内存清理步骤。旧 skill block 被新 skill block 截断替换
Reference 按需加载 启动时只解析 reference 的元数据（id, path, purpose），body 在 Phase 2 才读取
Phase 3 重复注入 每次 model call 都重新注入 skill block，导致 trace 重复。功能正确，cosmetic 问题
SkillFileMiddleware 独立运作 即使 SkillLifecycleMiddleware 已经注入了 reference 内容，LLM 仍可通过 read_file 读取 — 两条路径并存

10. 加载与卸载的判断逻辑详解

10.1 Middleware 怎么判断"什么时候加载什么 skill"

核心方法：_detect_target_skill(messages) — 每次 model call 之前调用，扫描 LLM 之前的输出（历史消息）。

扫描历史消息（从最新到最旧）
遍历 request.messages 中所有消息（reversed(messages)），逐条检查 LLM 的历史输出。
注意：检测的是 LLM 之前输出的消息，不是当前这次 model call 的输出。
Level 1 — JSON intent_code（优先级最高）
尝试将消息内容解析为 JSON，在以下位置查找 intent_code 字段：
• payload["frames"][i]["intent_code"] — protocol frame 中的意图码
• payload["frames"][i]["current_task"]["intent_code"] — 当前任务的意图码
• payload["intent_code"] — 顶层意图码
• payload["current_task"]["intent_code"] — 顶层当前任务
找到后通过 _intent_index[intent_code] → skill_name
消息内容: {"frames": [{"intent_code": "AG_TRANS", ...}]} → intent_code = "AG_TRANS" → _intent_index["AG_TRANS"] = "transfer-routing" → 返回 "transfer-routing"
Level 2 — 文本扫描已注册的 intent_code（兜底）
如果 JSON 解析失败或未找到 intent_code，则遍历 _intent_index 中所有已注册的 intent_code，
检查 LLM 输出文本中是否包含该字符串。
消息内容: "用户想要转账，意图为 AG_TRANS，需要提取收款人..." → "AG_TRANS" in content → True → _intent_index["AG_TRANS"] = "transfer-routing" → 返回 "transfer-routing"
未检测到 → 返回 None
如果所有消息都未匹配到任何 intent_code → 返回 None。
此时 middleware 执行 Phase 1（注入 metadata 摘要）或 Phase 3（保持当前 skill）。

_prepare_skill_context() 加载决策矩阵

_detect_target_skill 结果 self._loaded_skill 判断 执行动作
None None 首次调用，尚未识别任何意图 Phase 1：注入 metadata 摘要
"transfer-routing" None 首次检测到意图，还没加载过 skill Phase 2（首次加载）：加载 skill body + 所有 references
"transfer-routing" "transfer-routing" 同一个 skill，多轮对话中 Phase 3（持续注入）：重新注入 skill block
None "transfer-routing" 有已加载的 skill，但没检测到新意图 Phase 3（持续注入）：保持当前 skill
"bill-payment-routing" "transfer-routing" 检测到不同的意图！ 卸载 + 加载：卸载旧 skill，加载新 skill
Reference 的加载逻辑：
Reference 不是单独按需加载的 — 它随 skill body 一起在 Phase 2 一次性全部加载。
具体加载哪些 reference 完全由 SKILL.md frontmatter 的 references 字段决定：
_build_skill_block() 遍历 meta.references → 逐个 load_reference(skill_name, ref.id)。
声明了几个 reference 就加载几个。如果 skill 没有声明 references，就只加载 skill body。

10.2 Middleware 怎么判断"什么时候卸载 skill"

卸载触发条件只有一个：检测到新的、不同的 intent_code。

_prepare_skill_context() 中的卸载判断：

必须同时满足三个条件：
① target_skill != None — 检测到了一个意图
② target_skill != self._loaded_skill — 这个意图对应的 skill 和当前已加载的不同
③ self._loaded_skill != None — 当前确实有一个已加载的 skill

三个条件缺任何一个都不会触发卸载。

卸载时序（多任务场景）

时间点 _loaded_skill _detect_target_skill 三个条件 是否卸载
用户发"给张三转账500元，缴电费200元" None None 条件①不满足 否 → Phase 1
Model Call #1 输出了 AG_TRANS None "transfer-routing" 条件③不满足（没有已加载 skill） 否 → Phase 2（首次加载）
Model Call #2 提槽 "transfer-routing" "transfer-routing" 条件②不满足（同一个 skill） 否 → Phase 3
Model Call #3 调用 workflow "transfer-routing" "transfer-routing" 条件②不满足 否 → Phase 3
CompletionGate 触发，前端确认完成 "transfer-routing" —（无 model call） — 否（循环已终止）
用户发"继续"，LLM 推进到 AG_PAY_BILL "transfer-routing" "bill-payment-routing" ①✓ ②✓ ③✓ 全部满足 是 → 卸载 + 加载新 skill

不会触发卸载的情况

场景原因
同一 skill 的多轮对话（提槽、追问、补槽） target_skill == _loaded_skill，条件②不满足
_detect_target_skill 返回 None 历史消息中没有新的 intent_code，条件①不满足
当前没有加载任何 skill（_loaded_skill == None） 不存在可卸载的 skill，条件③不满足
任务完成（前端调用 /completion 接口） middleware 不会因"任务完成"主动卸载。_loaded_skill 保持不变，
只有当下一个任务的 intent_code 出现在 LLM 输出中，才触发卸载+切换
用户发送普通聊天（非业务意图） _detect_target_skill 返回 None，条件①不满足。
如果之前有加载过 skill，继续 Phase 3 保持当前 skill

卸载的实际操作

emit trace: skill_unloaded
记录日志和 trace 事件，标记旧 skill 被卸载。
skill_unloaded: 卸载技能: transfer-routing
更新内部状态：_loaded_skill = 新 skill name
self._loaded_skill = "bill-payment-routing"
_inject_skill_with_references() — 替换 system prompt
卸载 = 替换 system prompt 中的 skill block：
• 检测 system prompt 中是否有 "## Loaded Skill:" 标记
• 如果有 → 截断该标记之后的所有内容（旧 skill body + references 全部移除）
• 追加新 skill 的 block（body + references）
没有独立的"清除内存"步骤。卸载和加载是同一个操作的两个部分：截断旧 block + 追加新 block。
system_prompt = "...## Loaded Skill: transfer-routing\n\n{旧body}\n### Reference: slot_filling..." ↓ 截断 system_prompt = "..." ↓ 追加新 block system_prompt = "...\n\n## Loaded Skill: bill-payment-routing\n\n{新body}\n..."

11. Middleware 与 LLM 的交互协议

10.1 两条并行的 Skill 内容获取路径

路径 A — 被动注入（SkillLifecycleMiddleware）

Middleware 在每次 model call 之前自动修改 system prompt，注入 skill 内容。
LLM 不需要主动操作，不知道 middleware 的存在。
LLM 感知到的只是 "system prompt 里多了一段内容"。

Model Call 开始 → SkillLifecycleMiddleware.wrap_model_call() → 修改 request.system_message → 注入 "## Available Skills" 或 "## Loaded Skill: xxx" → handler(modified_request) ← LLM 看到修改后的 prompt → LLM 返回结果

路径 B — 主动读取（SkillFileMiddleware）

LLM 根据 Skill Loading Protocol 指令，主动发出 read_file function call。
Middleware 拦截 tool call，从 SkillRegistry 返回内容。
LLM 感知到的是 "我调用了 read_file 工具，拿到了文件内容"。

LLM 输出 tool_call: read_file("/skills/transfer-routing/references/workflow_request.md") → SkillFileMiddleware.wrap_tool_call() → 路径以 /skills/ 开头？ 是 → _resolve_virtual_path() → SkillRegistry.load_reference() → 返回 ToolMessage(content=reference_body) → LLM 收到 reference 内容
两条路径并存的原因：
• 路径 A（被动注入）是主要路径 — Phase 2 时 middleware 已经把 reference 内容注入到 system prompt
• 路径 B（主动读取）是补充路径 — 如果 LLM 需要再次查看某个 reference，或者想读取 Phase 2 未覆盖的文件
• 实际运行中，两条路径可能同时生效：system prompt 里有 reference 内容，LLM 又通过 read_file 读了一遍

10.2 deepagent AgentMiddleware 接口协议

Middleware 实现 deepagent SDK 的 AgentMiddleware 接口。SDK 在 agent 循环中自动调用 middleware 的 hook 方法。 Middleware 和 LLM 之间没有专门的通信协议 — middleware 通过修改 request/response 来间接影响 LLM 行为。

Hook 方法调用时机Middleware 可做的事Skill 相关用途

10.3 LLM 视角 — 它看到了什么

LLM 完全不知道 middleware 的存在。从 LLM 的角度，它只是在和一个带有 system prompt 和工具的 agent 环境交互。

LLM 看到的实际来源LLM 的理解

System prompt 中出现 ## Skill Loading Protocol SkillLifecycleMiddleware Phase 1 自动注入 "识别意图后要先 read_file 读 reference，再调 workflow_api_call"
System prompt 中出现 ## Loaded Skill: transfer-routing + body + references SkillLifecycleMiddleware Phase 2 自动注入 "我现在有了这个技能的完整提槽规则和 API 调用方式"

10.5 Middleware 链执行顺序图

7 个 middleware 按固定顺序执行。每个 middleware 有两类 hook：wrap_model_call（model call 前后）和 wrap_tool_call（tool call 前后）。 不是所有 middleware 都实现两类 hook。

# Middleware wrap_model_call wrap_tool_call 对 LLM 的影响
1 TaskProgressMiddleware 注入任务执行约束到 system prompt — LLM 看到串行执行、不自行完成任务等规则
2 FrontendContextMiddleware 注入 recommendTask / currentDisplay — LLM 看到前端推荐卡片和当前页面展示内容
3 CompletionGateMiddleware 检测 workflow 结果 → 终止循环 — workflow 返回后 LLM 不再被调用（循环被终止）
4 SkillLifecycleMiddleware Phase 1/2/3: 注入 skill 内容到 system prompt — LLM 看到技能元数据 / 完整 skill body + references
5 SkillFileMiddleware — 拦截 read_file(/skills/...) → 从 Registry 返回 LLM 调用 read_file 得到 skill 文件内容（虚拟路径）
6 WorkflowGatewayMiddleware — URL 白名单校验 + before/after hooks LLM 调用 workflow_api_call 被校验 URL，通过后执行 HTTP 调用
7 ProtocolOutputMiddleware 格式化输出为 AssistantProtocolFrame — LLM 输出被转换为标准协议帧格式
执行模型：
• wrap_model_call：按 1→2→3→4→5→6→7 顺序，在 LLM 调用前修改 system prompt 或决定是否终止循环
• wrap_tool_call：按 1→2→3→4→5→6→7 顺序，在 tool 执行前拦截或修改。只有 #5 和 #6 实现了此 hook
• 每个 middleware 可以选择：(a) 修改 request 后透传给 handler，(b) 直接返回结果（不调用 handler），(c) 不做任何事透传
