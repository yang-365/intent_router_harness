2. LLM 发出 workflow_api_call — 触发条件

LLM 怎么知道要调用 workflow_api_call？

Step 1: Skill reference 提供了 URL 和调用方式
workflow_request.md 中明确写了：
- 工具名：workflow_api_call
- URL：http://127.0.0.1:9877/agent-api/workflow-agent-1-1b14f16b/chatabc/use_as_tool
- body 格式：{ session_id, txt, stream, config_variables }
- 调用时机：AG_TRANS 槽位齐全且 executionMode=execute 时
Step 2: Skill Loading Protocol 指令引导
SkillLifecycleMiddleware 在 metadata summary 中注入了指令：
"识别到用户意图后，必须先通过 read_file 读取对应技能的 reference 文件，
了解提槽规则和 API 调用方式，然后再调用 workflow_api_call。
不要编造 workflow URL，必须使用 reference 文件中的完整地址。"
Step 3: LLM 发出 function call
LLM 根据 reference 中的 URL 和 body 格式，生成 tool_call：
tool_calls: [{ "name": "workflow_api_call", "args": { "method": "POST", "url": "http://127.0.0.1:9877/agent-api/workflow-agent-1-1b14f16b/chatabc/use_as_tool", "body": { "session_id": "test_002", "txt": "给张三转账500元", "stream": true, "config_variables": [ {"name": "custID", "value": "C0001"}, {"name": "sessionID", "value": "test_002"}, {"name": "slots_data", "value": "{\"payee_name\":\"张三\",\"amount\":500}"} ] } } }]

4. WorkflowGatewayMiddleware — 详细执行流程

4.1 URL 白名单校验

_check_url(request) — 提取 URL 并校验
从 tool_call args 中提取 url 字段，检查是否以白名单中的任何前缀开头。
args = _tool_args(request) url = str(args.get("url", "")) # self._allowed = { # "http://127.0.0.1:9877/agent-api/workflow-agent-1-1b14f16b/chatabc/use_as_tool", # "http://127.0.0.1:9877/agent-api/workflow-agent-bill/chatabc/use_as_tool", # "http://127.0.0.1:9877/agent-api/workflow-agent-payee/chatabc/use_as_tool", # } if any(url.startswith(prefix) for prefix in self._allowed): # → 通过！继续执行 else: # → 拒绝！返回错误 ToolMessage

✓ URL 在白名单中

handler 最终调用 workflow_api_call(method, url, body)（workflow.py 中定义的函数）
→ 详见第 5 节 "HTTP 请求与 SSE 解析"

执行所有注册的 after hooks（可选扩展点，异常不中断主流程）

记录返回结果长度和预览（前 500 字符）

✗ URL 不在白名单中

返回拒绝 ToolMessage — 不调用 handler
直接构造 ToolMessage 返回给 LLM，内容为错误说明 + 允许的 URL 列表。
工具函数不会被调用，不发送 HTTP 请求。

注意：URL 被拒绝后返回的 ToolMessage 的 name="workflow_api_call"，
CompletionGateMiddleware 会将其视为 workflow 结果 → 触发完成门控。
白名单拒绝也算任务完成（前端收到 completion_state=1）。

5. HTTP 请求与 SSE 响应解析

5.1 workflow_api_call() 函数执行

日志记录请求
logger.info("workflow_api_call method=%s url=%s body=%s", ...)
调用 _execute_workflow_sse(method, url, body)
使用 httpx.Client 发送 HTTP 流式请求。

5.2 _execute_workflow_sse() — SSE 流解析

发送 HTTP 请求（流式）
httpx.Client.stream(method.upper(), url, json=body)
发送带 JSON body 的 HTTP 请求，以流式方式读取响应。
with httpx.Client(timeout=60.0) as client: with client.stream("POST", url, json=body) as response: response.raise_for_status() # 逐 chunk 读取...
逐 chunk 累积 + SSE 分帧
每收到一个 chunk，累积到 buffer。遇到 \n\n（空行分隔符）时切分为独立 SSE event。
每个 event 交给 _parse_sse_event() 解析。
buffer = "" for chunk in response.iter_text(): raw_text += chunk # 保存原始响应（用于 fallback） buffer += chunk while "\n\n" in buffer: event_text, buffer = buffer.split("\n\n", 1) parsed = _parse_sse_event(event_text) if parsed is not None: events.append(parsed)
_parse_sse_event() — 解析单个 SSE event
提取 data: 行的内容，合并后尝试 JSON 解析。
# 输入： # "event:message\ndata:{\"content\":\"\",\"additional_kwargs\":{\"node_output\":{...}}}" # # 提取 data 行： # "{\"content\":\"\",\"additional_kwargs\":{\"node_output\":{...}}}" # # JSON 解析得到 dict

5.3 Workflow 服务端 SSE 响应格式（deepagent runtime）

deepagent workflow runtime 的 SSE 响应格式如下（mock_workflow_server 模拟了相同格式）：

SSE Stream（每个 event 由 \n\n 分隔）
event:message data:{"content":"","additional_kwargs":{"node_id":"mock_0","node_title":"Mock节点0","node_output":{"mock":"transfer-start","received":{...}},"timestamp":"2026-05-08 00:00:00"},"response_metadata":{},"type":"ai","name":null,"id":null,"tool_calls":[],"invalid_tool_calls":[],"usage_metadata":null} event:message data:{"content":"","additional_kwargs":{"node_id":"mock_1","node_title":"Mock节点1","node_output":{"mock":"transfer-check","result":"transfer_ready"}},...} event:message data:{"content":"","additional_kwargs":{"node_id":"mock_2","node_title":"Mock节点2","node_output":{"output":"mock-transfer-done","exception":null}},...} event:done data:[DONE]
关键：node_output 嵌套在 additional_kwargs 内部，不在顶层。
解析器必须从两个位置查找：event["node_output"] 或 event["additional_kwargs"]["node_output"]。

6. 响应解析 — 三级 Fallback

解析后的 events 列表 → 提取 node_output

检查 1：是否有 SSE events？
如果 events 列表为空（服务端没有返回有效的 SSE 帧）
→ Fallback A：返回原始响应文本
if not events: logger.warning("workflow returned no SSE events, returning raw payload") return _raw_output(raw_text) # → {"output": raw_text} 或 {"output": json.loads(raw_text)}
检查 2：最后一个 event 是否包含 node_output？
取 events[-1]（最后一个 SSE event），通过 _extract_node_output() 查找：
① event["node_output"]（顶层）
② event["additional_kwargs"]["node_output"]（嵌套在 additional_kwargs 内）
如果找到 → 正常返回
last = events[-1] node_output = _extract_node_output(last) if node_output is not None: return { "node_output": node_output, # 最终业务结果 "event_count": len(events), # event 总数 "events": events, # 完整 event 列表 }
检查 3：有 events 但没有 node_output
SSE 帧存在但没有 node_output → Fallback B：返回 raw events
logger.warning("workflow final event has no node_output, returning raw events") return { "output": events[-1] if len(events) == 1 else events, # 原始 events "event_count": len(events), "events": events, }

_extract_node_output() — 双位置查找

def _extract_node_output(event: dict[str, Any]) -> Any | None: """The deepagent workflow runtime may place node_output either at the top level of the event or nested under additional_kwargs.""" if "node_output" in event: return event["node_output"] # 位置 1：顶层 additional = event.get("additional_kwargs") if isinstance(additional, dict) and "node_output" in additional: return additional["node_output"] # 位置 2：嵌套 return None

三级 Fallback 总结

级别 条件 返回格式 output 字段内容
正常 events 非空，最后一个 event 有 node_output {"node_output": {...}, "event_count": N, "events": [...]} 提取的 node_output 业务数据
Fallback B events 非空，但没有 node_output {"output": events, "event_count": N, "events": [...]} 原始 SSE event 对象
Fallback A events 为空（无有效 SSE 帧） {"output": raw_text_or_json} 原始 HTTP 响应文本（如能 JSON 解析则为对象）
设计原则：无论 workflow 服务端返回什么格式，workflow_api_call 工具永远返回有用数据：
能解析 node_output 就用结构化数据，不能就把原始响应放进 output 字段。
LLM 和前端总能拿到 workflow 的返回内容。

7. 异常处理

workflow_api_call 的异常链

异常类型 触发条件 抛出的错误 LLM 看到什么
httpx.TimeoutException 请求超时（默认 60s） WorkflowExecutionError("workflow request timed out after 60.0s") ToolMessage with error content
httpx.HTTPStatusError HTTP 4xx/5xx 响应 WorkflowExecutionError("workflow HTTP 500: {body[:200]}") ToolMessage with error content
httpx.HTTPError 连接失败、DNS 解析失败等 WorkflowExecutionError("workflow HTTP error: {exc}") ToolMessage with error content
其他 Exception JSON 序列化失败等 WorkflowExecutionError("workflow call failed: {exc}") ToolMessage with error content
所有异常都转换为 WorkflowExecutionError（code="workflow_execution_error"）。
deepagent runtime 捕获异常并将错误消息包装为 ToolMessage 返回给 LLM。
LLM 看到错误后可能重试或告知用户失败。

8. CompletionGateMiddleware — 任务完成门控

8.1 触发时机

CompletionGateMiddleware 实现了 before_model hook — 在下一次 model call 之前检查。
不是在 tool call 返回时检查，而是在 deepagent 准备发起下一轮 LLM 调用时检查。

扫描所有消息，查找 workflow_api_call 的 ToolMessage
any(self._is_workflow_result(msg, ToolMessage) for msg in messages)
判断条件很简单：只要消息中存在 name="workflow_api_call" 的 ToolMessage，就触发。
不区分成功返回还是白名单拒绝 — 都算 workflow 结果。
@staticmethod def _is_workflow_result(msg: Any, tool_message_cls: type) -> bool: if not isinstance(msg, tool_message_cls): return False return getattr(msg, "name", "") == "workflow_api_call"
触发 → 终止 deepagent 循环
返回 {"jump_to": "end", "messages": [AIMessage(...)]}
deepagent runtime 收到 jump_to: "end" 后不再调用 LLM，直接结束循环。
附带的 AIMessage 包含一个 protocol frame。
completion_gate_triggered: 检测到workflow返回结果，终止agent循环，等待前端确认
输出 protocol frame
CompletionGate 构造的 AIMessage 内容：
{"frames": [{ "ok": true, "status": "waiting_assistant_completion", "completion_state": 1, "completion_reason": "workflow_result_available", "output": {} }]}
为什么 output 是空的？
CompletionGate 只负责终止循环，不负责提取 workflow 结果。workflow 的返回数据仍然在消息历史中的 ToolMessage 里。
前端通过 SSE stream 收到 trace events（包含 workflow_call_completed 的 result_preview）来获取详细结果。

13. 设计约束与边界

约束说明
URL 必须来自 skill reference Skill Loading Protocol 指令要求 LLM 从 reference 读取 URL，不能自己编造
URL 白名单由 TOML 配置 [deepagent].workflow_allowed_urls 中配置，不在框架代码中硬编码
白名单拒绝 = 任务完成 CompletionGate 不区分成功/拒绝，只要有 workflow_api_call 的 ToolMessage 就终止
任务完成必须前端确认 CompletionGate 设置 completion_state=1（等待），只有 /completion 接口才设 completion_state=2
解析失败不丢数据 三级 fallback 确保任何格式的 workflow 响应都能作为 output 返回
工具函数业务无关 workflow_api_call 只做 HTTP+SSE，不理解转账/缴费业务语义
node_output 双位置查找 兼容 deepagent runtime 格式（顶层或 additional_kwargs 内）
before/after hooks 扩展点 WorkflowGatewayMiddleware 支持注入自定义 hooks，after hook 异常不影响主流程
CompletionGate 在 before_model 触发 不是 tool call 返回时触发，而是下一次 model call 之前。这意味着 workflow ToolMessage 已经在消息历史中
